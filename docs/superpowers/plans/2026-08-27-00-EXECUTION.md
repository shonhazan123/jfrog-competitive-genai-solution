# Execution Orchestration — Per-Surface Research-Graph Rebuild

**Read this first. You are the orchestrator.** Your job is to drive the five implementation plans in this folder to completion, autonomously, in the right order, dispatching subagents to do the work. The human is away — do not wait for approval. When everything is done, post the summary described in the last section.

**Branch:** `jfrog_agent_v2` (already checked out). All work happens here.

**The spec (the authority every plan argues from):**
`docs/superpowers/specs/2026-08-27-per-surface-research-graphs-design.md` — when a plan is ambiguous or two plans disagree, the spec wins.

---

## 1. Model assignment (non-negotiable)

| Role | Model | Used for |
|------|-------|----------|
| **Reasoning / planning / review** | **Opus 4.8 (high)** | You (the orchestrator). Conflict scans, dependency decisions, rulings, reviewing a subagent's diff, deciding whether a plan's tests "pass enough" to advance. |
| **Writing / coding / testing** | **Composer 2.5 (fast)** | Every implementer subagent: writing source files, writing tests, running the suite at plan end, applying fixes. |

Always set the model explicitly when you dispatch. Never let an implementer run on Opus (cost) and never let a reasoning/review step run on Composer (judgment).

## 3. Autonomy rules

- **No approval waits.** The human is away. Never stop to ask "should I continue?" or post progress check-ins.
- **Always take the recommended approach.** Every plan already marks its recommended option; every open choice resolves to the spec's recommendation. Where a plan says "(Recommended.)", pick it.
- **Rulings, not stalls.** If two plans conflict, a plan is wrong, or a value is missing, decide it — spec is the binding authority — write a one-line ruling in the ledger (`Ruling: <decision> — <why> — <cost if wrong>`), and keep going.
- **Only four things stop you:** an irreversible/destructive op beyond this branch, a security-sensitive action, a push/merge to a shared branch, or a plan so broken every path is a guess. Nothing else.
- **Open values already decided for you:** the `jfrog_position` yardsticks for **CI/CD Integration** and **Developer Experience** (Comparison Task 1) — use the DRAFT text already written in spec §9 verbatim. Do not block on them.

## 4. Test policy (the human's explicit rule)

- **Implementers WRITE tests as they build each task, but DO NOT run them per task.** Skip the per-task "run the failing test / run it green" steps inside the plans — write the test file and the implementation, commit, move on.
- **Run the full test suite ONCE, at the end of each plan.** Only after every task in a plan is implemented.
- **Advance to the next plan only when the finishing plan's suite is green.** This is the gate between plans.
- **On failure at the plan-end run:** dispatch a Composer fix subagent with the failing output; it fixes and re-runs; repeat until green. Do not start the next plan while the current plan is red. If a suite cannot be made green after 3 fix rounds, stop and record a ruling describing the blocker (this is a "plan so broken" case).
- Tests are designed to run offline (LLMs, the embedder, and web_search are stubbed in every test) — a green run needs the app's normal test toolchain (Python env + the test Postgres the `session` fixture expects), not network or API keys. Bring that toolchain up before the plan-end run.

## 5. Wave schedule (parallelize only what doesn't contradict)

"Contradicting" = two subagents editing the same file. Parallelize work on **disjoint files**; serialize everything that shares a file.

### Wave 1 — Phase 0 (no parallelism)
Deletion order matters (detach wiring → delete functions → delete files → remove sources → purge data). Run Phase 0's tasks **sequentially** in the order written. One implementer at a time. Then run the suite; gate.

### Wave 2 — Foundation (partial parallelism)
These four tasks touch disjoint files — dispatch them as **one parallel wave**:
- Task 1 (migration + model columns)
- Task 2 (`agent/tools/web_search.py`)
- Task 3 (`agent/llm.py` embedder)
- Task 4 (`agent/graphs/research/skeleton.py`)

Then **sequentially** (each depends on the above):
- Task 5 (provenance — needs the embedder from Task 3)
- Task 6 (multi-run store + fan-out)

Then run the suite; gate.

### Wave 3 — the competitor set (prerequisite, single task)
Do **Signals Task 1** alone first (`entities.yaml`, `competitors.yaml`, `competitors.py`, and fix any entity-count assertions it breaks). Both Signals and Comparison depend on it. Commit it before the wave below.

### Wave 4 — the three agents' own files (parallel wave)
Each agent's **new-file** work is disjoint (its own `deps.py`, prompt, agent service, config, tests). Dispatch as **one parallel wave**:
- Industry: Tasks 1–3 (buckets config, gate deps, persist) — *skip* the `run_industry` re-export edit to `worker/jobs.py` for now.
- Signals: Tasks 2–3 (deps, persist) — *skip* the `worker/jobs.py` re-export.
- Comparison: Tasks 1–3 (dims config, deps, persist) — *skip* the `worker/jobs.py` re-export.

**Hold back every edit to a shared file** (`backend/worker/jobs.py`, `config/llm.yaml`, `client/src/api/client.ts`) — those are Wave 6.

### Wave 5 — read-path rewrites (parallel wave, disjoint files)
- Industry Task 4 (`industry_themes.py` → group by `theme_key`, delete `themes.yaml`)
- Comparison Task 4 (`comparison_matrix.py` → stance + 5 dims, delete `jfrog_components.yaml`)

These touch different files — parallel is safe.

### Wave 6 — integration of shared files (single implementer, sequential)
One implementer makes all the shared-file edits together, so they never collide:
- `backend/worker/jobs.py`: add the three re-exports (`run_industry`, `run_signals`, `run_comparison`).
- `config/llm.yaml`: add the `gate` and `synthesize` roles (once).
- Frontend: `client/src/api/client.ts` `runSurface(kind)` (once), then the three `Run this page` buttons + the Comparison grid frontend changes (Industry Task 5, Signals Task 4, Comparison Tasks 5–6).

Then run the **full** suite (backend + client); gate. This is the final green.

> If you prefer to isolate Waves 4–5 in per-plan git worktrees to run them truly in parallel, that is allowed — but you must still funnel every shared-file edit through Wave 6, and merge the worktrees before Wave 6.

## 6. Per-task dispatch loop (inside every wave)

For each task (or parallel batch of disjoint tasks):

1. **Dispatch a Composer 2.5 implementer.** Give it: the one plan file, the specific task number(s), the Global Constraints from that plan, and any interface names from earlier tasks it consumes. Tell it: *write the code and the tests, commit per the task's commit step, but DO NOT run tests* (per §4).
2. **Never dispatch two implementers that touch the same file at once.** Disjoint-file batches only.
3. **When it reports back, you (Opus) review its diff** for spec compliance and obvious defects. If it's wrong, send it back with the specific findings (up to 3 rounds), then escalate to a fresh Composer implementer with the findings.
4. **Record progress in a ledger** at `.superpowers/sdd/execution/progress.md` — one line per task: `Plan <name> Task <N>: complete (commit <sha>)`. This is your recovery map if context is lost; trust it over memory.
5. At **plan boundary**, run the suite (§4 gate) before the next plan.

Keep your own narration to one line between dispatches. Hand large content to subagents as file paths, not pasted text.

- **Phase 0:** interpret gone; noise sources removed; `reset_findings` exists; suite green. Pages will be empty — that's expected.

- **Whole build:** `POST /runs/all` fans out to all three; each page fills on its own run; full suite (backend + client) green.
